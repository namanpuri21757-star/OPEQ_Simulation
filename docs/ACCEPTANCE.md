# Acceptance

What has to be true before this is used with a real class, how each one is
checked, and where the check lives. Every row except the two marked **manual** is
an automated test that runs in `npm run verify`.

The two manual rows (M1 and M2) are the whole reason `docs/READINESS-REPORT.md`
says the app is not yet ready for a class. They cannot be automated: one needs a
real school network, the other needs real people. Both are written out step by
step in that report and rehearsed in `docs/DRY-RUN.md`.

Run it all with `npm run verify`. The quick subset, which leaves out the load
test and the browsers, is `npm run verify:quick`.

## Other browsers

Chromium is the browser the suite must pass in, and it does. Firefox and WebKit
are installed and were tried:

| Browser  | Result                                                                                                                                                                                                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chromium | All 5 specs pass, in about 1.5 minutes.                                                                                                                                                                                                                                                            |
| Firefox  | All 5 specs pass, in about 3 minutes.                                                                                                                                                                                                                                                              |
| WebKit   | A1 (axe), A2 (keyboard) and S2 (markup) pass, slowly - A2 alone takes 7 minutes. C1 fails on its own stopwatch: opening eleven browser contexts in WebKit on this machine takes longer than the 10 s the criterion allows, which is browser startup and not the server. F2 does not finish at all. |

Run them with `PLAYWRIGHT_BROWSERS=firefox,webkit npm run e2e`. They are not part
of `npm run verify`: a classroom chooses its browser, and a browser we do not
support should not stop a release.

Nothing specific to WebKit was found. What was found is that this machine cannot
run eleven WebKit contexts at once - the worker is killed or the test runs out of
time - so the two WebKit rows above are honestly "untested", not "failed". On a
machine with more memory they are worth running again.

Two things Firefox taught the suite, both now permanent:

- Every browser logs an error when a socket is cut off, and F2 kills the server
  on purpose. Those lines are ignored by name; the test then asserts that every
  screen reconnected, which is the thing that actually matters.
- Tab does not wrap round at the end of the document in Firefox the way it does
  in Chromium. The keyboard test now walks the tab order forwards and then
  backwards, which is both browser-independent and closer to what a person does:
  the minus buttons on the number stepper sit before the field, so reaching them
  from the field is Shift+Tab.

## How the slow checks are set up, and why

Three deliberate choices are worth knowing about, because a reader would
otherwise think the tests had been made easier.

**The load test and the browser test turn the timers up.** Both use the
`test-fast` preset for its 12 years and its schedule, but give each year a
classroom-length timer instead of five seconds. Five-second years exist so a
developer can watch a whole game in a minute. With 18 terminals, or with nine
browsers typing real numbers, the clock would close a year before the room had
finished, every missing decision would be filled in automatically, and "no
decision was lost" would be impossible to state. The timers are a setting a
teacher chooses; the thing under test is everything else.

**The load test waits out the message rule.** One message per three seconds per
team (SPEC section 6) is correct behaviour, and a game played in seconds hits it.
The test waits rather than counting a correct refusal as a lost message.

**The privacy scan reads the wire, not the view builders.** In the browser test
it collects the actual socket frames each page received and searches those. A
field added to a view tomorrow is searched too, because the scan works on
strings and knows nothing about view shapes.
